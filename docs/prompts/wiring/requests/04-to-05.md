# 04 (Discovery) → 05 (Review)

What Discovery now writes and reads that Review's wiring has to agree with. Nothing here blocks 04; all of
it is already implemented on Discovery's side and is described so Review can read it rather than guess.

## 1. A queue is a filter, not a copy

*Send N unjudged to Review* (§7.4) does **not** duplicate detection rows. `POST
/api/discovery/runs/{run_key}/review` records a queue descriptor and nothing else:

```json
{ "name": "Discovery · drop_detection_v1 unjudged", "run_key": "drop_detection_v1",
  "run_group_id": 12, "n": 41, "created_at": "2026-09-21T…", "source": "discovery run",
  "blind": false, "writes": "adjudications" }
```

It lives in `discovery_sessions.state_json` under `review_queues`, and `GET /api/discovery/queues` returns
the list. The queue's *contents* are `Working.review.queue_state.ReviewQueue(conn,
run_group_id=<run_group_id>, adjudication_status="unadjudicated")` — the same object Review already has 18
tests for. Two consequences:

- a verdict Review writes immediately changes the count Discovery shows, with nothing to keep in step;
- returning to Discovery refreshes the score (§7.4) because the scoreboard reads `adjudications` live.

**The ask:** read the queue through `run_group_id`, not through a copied row set. If Review would rather
have a real `review_queues` table (name, source, blind, write target, filters — §10.1's five queue kinds),
say so and I will add it additively to `Working/database/schema.py`; the descriptor above is the shape I
would give it.

## 2. A superseded run must not reach a queue

`runs.superseded_at` and `runs.superseded_by_run_id` are new (additive, this prompt). §7.4's *Discard run*
sets `superseded_at` on every run of the fan-out and writes **no** adjudications and **no** annotations —
that is the whole point of the column, because a bulk discard turned into thousands of `not_interesting`
human verdicts would poison the RQ5 divergence measurement invisibly.

**The ask:** `ReviewQueue` should exclude runs with `superseded_at IS NOT NULL` (it does not today —
`queue_candidates` has no such filter). A discarded run's detections stay in the table on purpose, so
without the filter they keep arriving in Review after the researcher discarded them.

## 3. §4.7 — a rediscovery is not put to the researcher twice

Discovery already marks every seeded-search candidate that matches an existing human span:
`candidates[].judged` and `candidates[].verdict`, matched under the §4.6 rule
(`Working.discovery.matching`, reciprocal IoU ≥ 0.5 **and** onset agreement within 0.25 × the candidate's
own duration). The scoreboard's **already judged** column is the same computation against verdicts that
existed *before the run started*.

**The ask:** Review's queue should carry the prior verdict on a candidate that has one, and default to not
re-asking. The matching rule is `Working.discovery.matching.rule_from_settings(conn)` — Settings › Analysis
defaults, keys `iou` and `onset`. Please use that function rather than `Working.compare`'s
`SIMILARITY_IOU_THRESHOLD` (0.8, overlap only, no onset term), so one rule holds across both workspaces.

## 4. Verdicts Discovery expects to be able to read back

- `adjudications` for a verdict on a machine detection (the table is empty today, so every "already
  judged" cell on this machine currently comes from `annotations` written before the run).
- `annotations` with verdict `seed` for *Take span for Review* — Discovery's **Explore selection** seed
  source reads exactly those rows (`GET /api/discovery/seeds`).
