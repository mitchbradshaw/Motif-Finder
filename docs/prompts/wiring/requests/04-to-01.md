# 04 (Discovery) → 01 (Analyse / blocks / the job model)

Four things Discovery found in the block and run machinery. None of them blocked this prompt — each has a
default taken and named on the page — but all four are cheap and belong to files Prompt 01 owns.

## 1. `detection.seed_matches` has no exclusion-zone parameter (P1)

Spec §7.6 locks the seeded search's trivial-match guard to **m/2** and the parameter card draws it as a
locked value. The block calls `stumpy.match(q, x, max_matches=k, max_distance=md)` with no `excl_zone` and
no `query_idx`, so the search actually runs under stumpy's own default of **m/4**, and the self-match bin
the histogram shades is not the one the search excluded.

Discovery does not draw "m/2" over that. `Working.discovery.seeded_search.recommended_params` returns an
`exclusion_note` stating the real guard, and the bridge puts it on the seed page and in the run's params.

**The ask:** add `exclusion_zone` (samples, default `m // 2`) to `Adapters/detection_seed_matches.py` and
pass it through — `stumpy.match` takes `query_idx`, which sets the zone around the query when the query is
a subsequence of the same series. Two lines plus a test that a match inside m/2 of another is dropped. When
it lands, delete the note: `Working/discovery/seeded_search.py::recommended_params` is the only caller.

## 2. `detection.seed_matches` declares no `estimate`, so a seeded-search plan costs 0 s

`webui/server/chain.py::estimate` treats a block with `estimate=None` as free, and
`Working.hpc.job_export.route_recipe` then routes a sixteen-channel whole-recording seeded search to
`local`. Discovery refuses to report that: `Working.discovery.fanout.plan` returns
`route: "unknown"` with the uncosted step indices named, and §7.1's *Preview on a sample* supplies a
**measured** number instead (on the real run: 10.32 s for one hour of one channel → 41 s per channel).

**The ask:** an `estimate` hook on `detection.seed_matches`. It is a `stumpy.match` over `n` samples with a
query of `m`, i.e. O(n log n) with a constant that `Working.block_cost.register_cost_model` can calibrate
like the others. Until then the honest answer stays `unknown`, which is the right answer but a worse one.

## 3. `fan_out_recipe` cannot be cancelled between targets

`Working.run_groups.fan_out_recipe` forwards `should_cancel` to `execute_recipe`, which checks it before
each *step*; a cancel therefore raises `RecipeCancelled` out of the whole call and takes the `run_group_id`
with it, so a cancelled fan-out leaves a group nobody can read. `Working.discovery.fanout.start` runs the
same primitives (`create_run_group`, `materialize_target`, `run_paired_recipe`, `update_run`) with the
cancel checked **between** targets and an `on_target_done` callback the job model needs for per-channel
progress. That is a second loop over the same pieces, which I would rather not have.

**The ask:** give `fan_out_recipe` an `on_target_done(index, total, row)` hook and a between-target cancel
that returns `{run_group_id, runs, cancelled}` instead of raising. `Working.discovery.fanout.start` then
collapses into a call to it; I will do that edit if you add the hook.

## 4. The held-out check is not a pre-flight

`execute_recipe` raises `HeldOutRecordingLocked` on `recipe['recording_id']` from inside the fan-out loop,
so a scope containing a held-out channel runs the earlier targets, writes their `runs` rows, and only then
refuses. `Working.discovery.fanout.plan` filters the target list first and names the refusal, and the
bridge returns 423 before anything starts — but the core-level hazard is still there for any other caller.

**The ask (optional):** a `check_targets(recipe)` in `Working/run_groups.py` that validates every fan-out
target before the first one executes, raising with the whole list of offending targets rather than the
first one reached.
