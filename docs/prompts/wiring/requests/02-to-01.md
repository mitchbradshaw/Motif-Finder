# Requests from Prompt 02 (settings / registration) to Prompt 01 (analyse / explore / jobs)

Worked around locally where noted; none blocks 02.

- **Explore's recording menu needs no change** (verified): `GET /api/recordings` (`server/corpus.py::recordings`)
  now skips rows with `recordings.active = 0`, so a recording registered on Settings › Datasets appears in the
  menu and an unregistered one leaves it. Nothing to do unless Explore caches the list across navigations —
  if it does, refetch on focus.
- **Analyse source picker: offer registered artifacts.** `api.ts::getRegistry('matrix_profile' | 'window_matrix'
  | 'window_set' | 'encoding')` returns `registered[]` rows bound by content (`recording_id`, `channel`,
  `span_start/end`, `fs`, `params.config_hash`, `path`). A registered matrix profile with the right `m` and span
  can seed `detection.matrix_profile`'s resume (`Adapters/detection_matrix_profile.py` reads `RESULTS_DIR`);
  a registered window matrix can be the `windows` side-input of `catalogue.classifier`. The rows carry
  `manifest` (the sidecar) for the provenance chip. Not wired by 02: the picker is yours.
- **Jobs › Upload → continue the paused run.** `POST /api/registry/hpc_result/register` on a bundle under
  `HPC/results/<job>/` runs the P24 checks (recipe hash, per-channel shape, length, finite values) and, when
  the recipe hash matches a run whose status is one of `paused | waiting | pending | queued | hpc`, returns
  `facts.paused_run_id` (also in the row's `params_json`). 02 writes the `registered_artifacts` row and, when
  the bundle carries a `manifest.json`, imports it through `Working.manifest.import_manifest`. **Continuing the
  paused run from the next stage is the job model's step**: read `paused_run_id` from the registration and
  resume there. The status vocabulary above is 02's guess — if `jobs.py` uses another word for "paused at a
  stage over the local limit", add it to `Working/registration/kinds.py::_PAUSED_STATUSES` (one tuple).
- **Blocks page reads `/api/adapters` and the settings table.** Settings › Blocks lists what `GET /api/adapters`
  returns (name, signature, `known_broken`) and stores the on/off toggles as `settings` rows
  (`page = 'blocks'`, key `block.<stage>.<algorithm>.on`). If the insert modal should hide a disabled block,
  read `GET /api/settings/blocks` → `values` (a missing key means on). Not enforced server-side by 02.
- **Settings › Nulls / Analysis defaults values** are in the `settings` table under pages `nulls` and
  `analysis-defaults` (keys as the fixtures name them: `null.<kind>.method`, `null.<kind>.draws`, `alpha`,
  `rule.<block>.<param>`, `iou`, …). `preprocessing.surrogate` should read the per-kind defaults from
  `GET /api/settings/nulls` when a page passes none (D6 of the wiring plan).
