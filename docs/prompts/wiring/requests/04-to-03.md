## 1. What Discovery means by "Library exemplar" today

`GET /api/discovery/seeds` offers §7.6's three seed sources, in this order of preference:

| Source | Where it comes from now | What it should come from once 03 lands |
|---|---|---|
| **Library exemplar** | `motif_entry` rows if any exist; **otherwise** the 24 deepest pure events of `DATA/library_seed/drop_motifs5/motifs` (410 extracted events, `PROVENANCE.md`: not regenerable) | `motif_entry` — no change needed on my side |
| **Family medoid** | one per `span_key` of the same store (16 families), the member whose `drop_depth_mv` is closest to the family median | whatever 03 calls a family, if it exposes a medoid |
| **Explore selection** | `annotations` with verdict `seed` (Explore's *Take span for Review*, Prompt 01) | unchanged |

The `motif_entry` branch is already written and is tried first (`webui/server/discovery.py::_seed_candidates`),
so the moment 03 imports the events the seeds become Library entries with no edit here. It needs only
`recording_id`, `start_idx`, `end_idx` on the row — the three columns the schema already has.

Every payload says which source it used, and the seeds route carries a `note` naming the store while the
library is empty, so the page never claims a Library it does not have.

## 2. A seed is content-addressed, and does not need an entry id

A seed id is `"<source>:<recording_id>:<start_idx>:<end_idx>"` and resolves through
`Working.discovery.seeded_search.seed_from_content`, which hashes the samples themselves. The recipe binding
is the standard `library_exemplar` one with `entry_id: 0`:

```json
{"source_kind": "library_exemplar", "entry_id": 0, "source_file": "M2_aug_concat_fs1.mat",
 "channel": 15, "start_idx": 289550, "end_idx": 289686}
```

`Working.side_inputs._resolve_library_exemplar` never reads `entry_id` — it resolves by
(source_file, channel, span), which is what makes an exported recipe resolve on another machine.

**The ask:** when 03 promotes a span to `motif_entry`, Discovery would like to pass the real `entry_id`
through so the run's recipe records which entry it searched for. Tell me the promotion function's signature
(or the route) and I will thread it; nothing breaks meanwhile, because `entry_id: 0` resolves identically.

## 3. §4.2 — a search that re-finds a member

Discovery marks a seeded-search candidate `judged: true` with its `verdict` when it matches an existing
human span under the §4.6 rule (`Working.discovery.matching`). It does **not** currently resolve a match
onto a `motif_member` row, because there are none. §4.2/§4.7 say a re-run should resolve onto the existing
member rather than create a second one.

**The ask:** name the function that takes (recording_id, start_idx, end_idx) and returns the member it
belongs to, if 03 builds one. `Working.database.runs.find_motif_entry_id_for_content` exists and is what
`Working/templates.py`'s carry mode already uses; if 03 keeps that as the lookup, say so and I will call it
from the seeded-search result so a match carries its family.

## 4. Templates are shared, and §4.8 binds both of us

Discovery's template picker reads the real `templates` table through `webui/server/templates.py` (the nine
canonical rows). §8.9 gives the Library a Templates section over the same rows.

**The ask:** §4.8 — "Scores belong to runs, not to templates … **Never a bare number on a template card**".
Discovery's cards carry `lastScore` as a sentence with its scope attached
(`"precision 62 % over 13 reviewed detections · 2 ch · 1.4 h"`), or the words `not yet scored`. Please use
the same rule on the Library's cards; the computation is
`Working.discovery.scoreboard.score_runs(conn, run_ids)["total"]`.
