# Ticket #12 evidence audit — the four research docs, adversarially checked

**Produced** 2026-09-14 for wayfinder ticket #12 (*Select the stack for the rebuilt interface*) on map #4.
**Method.** One reader per research doc extracted its load-bearing claims (claims whose falsity would move the stack choice). One skeptic per doc then tried to refute each factual claim against primary sources (GitHub API issue state, official docs, this repo at the cited line). A synthesis pass compared all four and read map #4, ticket #12 and ticket #9's resolution.
**Caveat.** The verifiers are agents too. Where this audit and a research doc disagree, the audit is the better-checked claim, not the final word — re-check anything the decision will actually rest on.

## 1. Convergences (two or more docs, independently)

- Large-signal point count does not separate candidates once the existing bucketed min/max decimator is assumed. frontend-stack, plotting-libraries and inheritable-projects each say so on their own, and the repo confirms it: UI/plots.py:156 sets MAX_RENDER_POINTS=40000, UI/plots.py:311 is _minmax_decimate, and UI/plots.py:330 records 12.1 ms on 2.6M samples. Two hedges apply. The 12.1 ms is kernel-only on random data. core-transport and the inheritable-projects verification both note that a non-Python frontend still needs a transport to reach the decimator, which lives in UI/, and that end-to-end zoom latency has never been measured.
- The blank-pane AssertionError came from HoloViews' DynamicMap one-element-type rule (Curve+Image), and Panel's callback handling reduced it to a server-log WARNING. frontend-stack's project-bug-mechanism claim and plotting-libraries' blank-pane-root-cause claim both say this, and the UI/plots.py:43-63 docstring records it. Both verifications confirm the mechanism: the assertion is raised in holoviews core ndmapping._item_check.
- Silent failure is not purely a Panel artefact. HoloViews itself treats at least a KeyError raised in a DynamicMap callback as an empty frame (holoviz/holoviews#2827, open since 2018). frontend-stack cites it. The plotting-libraries verification pulled it in independently to correct that doc's 'Panel's only role' framing. Both verifications also say #2827 is a narrow, KeyError-specific proposal and not a general 'all exceptions become empty frames' design.
- Panel's failure surface is a Python-to-BokehJS channel, not a truly in-process renderer. The core-transport verification (Bokeh server docs), the frontend-stack verification (tests/ui/conftest.py console gate) and CLAUDE.md ('a present pane that throws in the browser') all say so. A Panel rebuild should therefore be scored like NiceGUI/Flet (a networked, Python-authored UI) on render-failure legibility.
- A browser console-error assertion is not unique to Dash or NiceGUI. Playwright already gives Panel the same thing, and this repo has it at tests/ui/conftest.py (the console_errors gate). The frontend-stack verification checked the repo for this. The plotting-libraries doc also leaves loud failure unverified for most candidates, so no doc demonstrates that one stack has a unique loud-failure primitive.
- Bokeh static export needs a headless browser (Playwright or Selenium), has no native PDF, and its SVG backend slows down with many glyphs. frontend-stack's claim and plotting-libraries' bokeh-export-limits claim (confirmed against current Bokeh docs) both say this. Plotly's Kaleido >=1.0 also needs an installed Chrome/Chromium. Both verifications confirm it, so Plotly and Bokeh sit in the same dependency class for export.
- hv.save(obj, fmt, backend='matplotlib') selects the backend per call (confirmed in installed holoviews 1.23.1). A HoloViews-based stack can export through Matplotlib without changing the interactive Bokeh pipeline. That is a two-renderer arrangement, with styling options declared per backend. This comes from the frontend-stack verification. plotting-libraries independently ranks Matplotlib as the gold-standard vector exporter.
- PyQtGraph has a documented range-changed signal (sigRangeChanged/sigXRangeChanged, ViewBox.py:90-93) and documents SVGExporter as 'the preferred method for generating publication graphics'. plotting-libraries confirms both. frontend-stack independently treats Qt/PySide6 as the structural outlier, with no browser and in-process with Working/.
- Canvas-only JS chart libraries (uPlot, Lightweight Charts) have no vector export. plotting-libraries confirms this by absence, and frontend-stack separately notes uPlot has no built-in export. A JS stack built on either would need a second tool for publication figures.
- Nothing substantial is available to inherit wholesale. For the chain, a hand-built composition surface is likely on every stack: inheritable-projects found no embeddable linear chain-editor component, and frontend-stack found no documented discriminated-union-to-renderable pattern. The hedge is that the absence claim was refuted as worded, because CellProfiler exists as a standalone desktop application.
- The recipe-prefix-hash step cache sits below the frozen boundary. It is at Working/execution.py:108 _recipe_prefix_hash, and UI_CONTEXT §4.1 lists it as frozen. inheritable-projects and core-transport both verify this, so the 'parameter edit hits prefix cache' slice step needs the same core work on every stack. What differs is glue, for example Streamlit's rerun model or Dash callbacks. The boundary already leaks, though: UI/analyse/chain_state.py:43 imports the private _recipe_prefix_hash (map #4 note 4, core-transport).
- render_value (UI/plots.py:2206) imports holoviews, numpy and param, not Panel. It is a roughly 20-line if-chain over seven type names returning HoloViews objects. The frontend-stack verification established this, and it is consistent with inheritable-projects' dispatch-by-type precedent (nwbwidgets default_neurodata_vis_spec, confirmed). Its head start therefore applies to any HoloViews-renderable host, and the dispatch contract itself is cheap to port. The cost is in the per-type _render_* functions.
- Cancellation is cooperative and checked once per step (Working/execution.py:328). The only way to stop work mid-step is a hard process kill, which skips the except handlers and leaves runs.status='running'. core-transport and its verification both establish this, and map #4 note 4 says the same.

## 2. Contradictions

- plotting-libraries vs frontend-stack, on where silent failure lives. plotting-libraries says 'Panel's only role was swallowing the exception' and that HoloViews' role was only the type assertion. frontend-stack says HoloViews 'interpret[s] exceptions as empty frames' (#2827) and prescribes routing around DynamicMap callbacks. Verified position: both layers contribute. HoloViews maps KeyError to an empty frame, and Panel logged the AssertionError. Neither doc's remedy (avoid DynamicMap, or stay in-family with a Plotly pane) is shown to escape Panel's callback error handling.
- core-transport vs the repo and CLAUDE.md. core-transport D2 says Panel/Streamlit/Dash are 'truly in-process', that failures are 'visible by default', and that 'there is no transport layer here to fail silently'. CLAUDE.md and UI_CONTEXT §5 record a silently blank pane that throws in the browser. The Bokeh server docs describe a Python-to-BokehJS sync channel.
- The repo contradicts itself on what the incident looked like. The UI/plots.py:43-63 docstring says it was 'only a WARNING in the server log'. The tests/ui/conftest.py docstring says 'a blank pane with a clean Python traceback and a loud browser console. Nothing on the Python side can see it.' Which account is right decides whether a browser console gate (Playwright or Dash get_logs) would have caught it.
- Incident count. The binding constraints, map #4 and ticket #12 say 'three times'. CLAUDE.md, UI_CONTEXT.md §5 and tests/ui/conftest.py say 'twice'. frontend-stack uses both numbers. Only one incident (Curve+Image) has a documented mechanism.
- inheritable-projects vs UI_CONTEXT.md and ticket #9, on the chain layout target. inheritable-projects treats Part 2's horizontal fixed-width-card canvas (T57) and filmstrip as 'already decided'. UI_CONTEXT §3/§4.2 labels them 'Current mechanism' and marks all of UI/ as open. Ticket #9's resolution says Analyse 'uses vertical chain rows on one shared time axis (P1)', which is not the horizontal card canvas. CLAUDE.md, meanwhile, says Part 2 replaced the vertical staged list. The node-graph and Qt dismissals in inheritable-projects rest on the superseded premise.
- inheritable-projects vs plotting-libraries, on plotly-resampler hosting. inheritable-projects says Dash is optional and that FigureWidgetResampler needs 'no server'. The pyproject lists dash>=2.11.0 as a required dependency, and FigureWidgetResampler needs a running IPython kernel. plotting-libraries says it cannot plug into Panel. Its verification says there is no shipped integration but that manual wiring to Panel's Plotly `viewport` param is plausible.
- frontend-stack vs plotting-libraries, on PyQtGraph at the payload. frontend-stack cites ~30k points at 60 Hz as 'comfortably inside' the 40k payload, but 30k is below 40k. plotting-libraries says PyQtGraph 'outscored every other candidate', while its own table leaves PyQtGraph's loud-failure cell unverified and gives D3 equal or better viewport and export marks.
- frontend-stack on Qt, internally. The heading says 'rendering and export are the same library', but the content has interactive render in PyQtGraph and export in Matplotlib (FigureCanvasQTAgg). plotting-libraries offers a different single-library route: PyQtGraph's own SVGExporter.
- core-transport, internally. A2 wires client disconnect to should_cancel, so a page reload cancels the run. A4 and the table say the run 'survives' reload because the runs row can be re-polled. The doc also calls Pyodide's Worker.terminate() 'uniquely' able to bypass crash-safety, while its C2 text shows that Windows kill() of a sidecar or child is equally forceful.
- core-transport vs the repo, on the reload channel. The doc says runs.current_step/status is written 'before and after each step'. Working/execution.py writes current_step before each step (:335) and status only at the end or on failure (:442, :454, :458). The row shows which step started, not which finished, and a hard kill leaves status='running' forever.
- Map #4 vs the verification, on render_value. The map says 'its implementation is Panel-bound'. UI/plots.py imports holoviews and param, not Panel, so it is HoloViews-bound.
- frontend-stack vs the Svelte docs. The doc frames Svelte 5 runes as a forced wholesale replacement. The migration guide says Svelte 4 syntax is still supported and can be mixed. React, held up as the stable contrast, removed ReactDOMTestUtils and deprecated react-test-renderer in React 19, which is its own recent churn in testing idioms.
- Brief scope vs doc coverage. The binding criteria put agentic throughput first and publication export as required. inheritable-projects scores neither. plotting-libraries does not score throughput and leaves loud failure mostly unverified. core-transport does not analyse the six non-Signal interchange types crossing a transport. Only frontend-stack attempts throughput at all, and its key evidence there is partially confirmed or refuted.
- Ticket #12 scope vs evidence. #12 keeps 'how the frontend reaches the core' out of scope. core-transport shows that the transport shape is largely set by the stack family: in-process Python, FastAPI+SSE/WS, or a sidecar. It also shows that transport determines cancel and reload behaviour and one confirmed silent-failure class (Tauri kill). The decision cannot be fully separated from transport.

## 3. Do not rely on — refuted, partial, or unverifiable load-bearing claims

- 'holoviz/holoviews#2827 shows a maintainer confirming DynamicMap interprets exceptions as empty frames' as a general, current design. Corrected: #2827 is an open 2018 proposal saying a KeyError is deliberately treated as an empty frame, with explicit Skip/Empty exceptions proposed. Nobody has checked that it reflects current code in holoviews 1.23.1. #707 is closed and obsolete (generator mode is deprecated). #5424 is a Jupyter-only debugging complaint. None of the three is the project's mechanism.
- 'Dash and NiceGUI carry the only concrete loud-failure test primitives; Panel has no equivalent.' Corrected: Dash's get_logs() is Chrome-only and reads SEVERE console logs. Percy is an external token-gated service, not built in. NiceGUI's `user` fixture is a browserless simulation that cannot prove paint, and no NiceGUI fixture is documented to fail on console errors. Panel gets the same console gate through Playwright, and this repo already has it (tests/ui/conftest.py). None of them catches a server-side exception that is only logged.
- 'The blank pane is an instance of #2827' and 'UI_CONTEXT.md documents Curve+Image'. Corrected: the incident is recorded in the UI/plots.py:43-63 docstring and in map #4. It was a type-assertion AssertionError logged by Panel's callback handling, not the KeyError-to-empty-frame path. docs/agents/UI_CONTEXT.md does not describe the Curve+Image mechanism.
- 'Datashader was not the culprit, confirmed via an unrelated issue hitting the identical assertion (#2359).' Hedged: the assertion does originate in HoloViews core. But #2359 is a matplotlib-backend report whose user says the plot 'still seems [to] render and work fine', so it does not show the blank-pane symptom. 'Panel's only role was swallowing' rests on the repo's own comment, with no check against Panel source, and HoloViews also swallows some exceptions (#2827).
- 'Every candidate handles the payload: Plotly Scattergl 2-3M, uPlot 10M+, PyQtGraph fine at 40k.' Corrected: Bokeh's ~25k WebGL threshold is confirmed. uPlot's README gives about 100k points/ms and no 10M+ figure. Plotly's 2-3M figure and its ~8 WebGL-context limit are unverified (the docs fetch failed). PyQtGraph's cited 60 Hz ceiling (~30k) is below the 40k cap. Multi-plot density (ticket #9's ~22-plot atlas) is unexamined for every candidate.
- 'Qt export and render are the same pipeline' and 'pytest-qt signal testing sidesteps did-it-paint'. Not checked. Receiving a signal proves code ran, not that pixels were painted. PyQtGraph for render plus Matplotlib for export is two pipelines. PyQtGraph SVGExporter is the single-library alternative, and its publication quality is unassessed.
- 'Bokeh export recipe is conda install selenium phantomjs pillow' and 'switching HoloViews to matplotlib changes the interactive pipeline'. Corrected: the PhantomJS text is outdated Bokeh 1.x documentation. Current Bokeh uses Playwright or Selenium. hv.save accepts backend= per call, so Matplotlib export leaves the interactive Bokeh render unchanged, with styling options declared per backend.
- 'Svelte 5 replaced its reactivity model wholesale; React has had a stable testing idiom.' Corrected: runes replace the model and the codemod has documented gaps, but Svelte 4 syntax still works and can be mixed in. React 19 removed test-utils (except act) and deprecated test-renderer. React hooks being stable since 2019 was not verified.
- 'Reflex fails on Node 22+ with ERR_REQUIRE_ESM (open issue #5983).' Refuted: the issue closed 2026-09-10, and a maintainer says Reflex 0.9.9+ (react-router v8) addresses the cause. This is no longer evidence against Reflex. The pytest-guidance half was not checked.
- 'Streamlit's rerun model structurally mismatches the prefix cache.' Premise confirmed (the whole script reruns). Whether it is a real mismatch is unchecked, since a rerun can call the core's own prefix cache.
- 'Seven-type rendering is Native on Panel, custom everywhere else.' Not checked, and its premise is weak. render_value is HoloViews-bound, not Panel-bound. The dispatch is about 20 lines. Per-type renderers are the real cost on any stack, including a rebuilt Panel.
- 'No linear-only, typed pipeline editor exists; every visual pipeline tool is a node graph.' Refuted: CellProfiler is maintained (pushed 2026-09-10, BSD-3) and has a linear ordered module list with named inputs. The claim that holds is narrower: no embeddable linear chain-editor component was found for any candidate web stack, based on a single search.
- 'Constraining React Flow to a line is strictly worse than a hand-built card canvas' and 'Qt is a cost against the committed browser target'. Not checked, and both rest on the false premise that Part 2 mechanisms and a browser target are binding. UI_CONTEXT marks them as current mechanism and open.
- 'plotly-resampler: Dash optional; FigureWidgetResampler needs no server.' Corrected: dash>=2.11.0 is a required dependency, alongside pandas and orjson. FigureWidgetResampler needs a running IPython kernel. It is untested on a 2.6M-point trace and defaults to 1000 points per view.
- 'The prefix cache is conceptually identical to DVC stage caching.' Corrected: it is analogous. It uses a recipe-prefix key, whereas DVC hashes each stage's dependencies.
- 'NWB, neurosift and sortingview all dispatch by type.' Corrected: this is confirmed for nwbwidgets only. neurosift is unverified. sortingview looks like layout composition.
- 'Plotly's Kaleido export is a shared, clean path, better than Bokeh.' Corrected: formats and same-Figure export are confirmed. Kaleido >=1.0 requires an installed Chrome (a get_chrome helper exists), the same dependency class as Bokeh. WebGL traces rasterise inside vector output, and Plotly Express switches to WebGL above 1k points.
- 'ECharts startValue/endValue are unreliable for slider zooms.' Hedged: the cited issues are closed and #10700 may have added the parameters. getOption() is a community workaround. SVG renderer performance at 40k points, or at atlas density, is unbenchmarked.
- 'uPlot/Lightweight Charts have no vector export.' Established by absence only. Lightweight Charts has a raster takeScreenshot().
- 'Lightweight Charts logical range returns sample-index bounds identical to x_range_to_sample_bounds.' Unverified and likely wrong. Logical indices index the loaded, decimated bars, not the raw samples.
- 'Observable Plot pan/zoom open since 2024-11-01.' Corrected: 2024-11-01 is updated_at. Still unshipped as of docs and v0.6.17 (2025-02-14).
- 'Plotly-Resampler cannot plug into Panel.' Hedged: no Panel integration ships. Manual wiring to Panel's Plotly `viewport` param is plausible but untested.
- 'Panel/Streamlit/Dash are truly in-process with no transport layer to fail silently; the in-process frontend is the ceiling.' Corrected: the core callbacks, cancel flag and server-side exceptions are in-process. Rendering crosses a WebSocket (Bokeh server to BokehJS for Panel, WebSocket for Streamlit, HTTP from a React client for Dash), and browser-side failures there can be silent. This repo has already seen it happen.
- 'FastAPI + sse-starlette with a thread+queue bridge is a direct mechanical mapping with no protocol design.' Corrected: it is workable and pip-only. It still needs a thread-to-loop handoff (asyncio.Queue is not thread-safe, so call_soon_threadsafe or similar), hand-wired disconnect-to-cancel, and event framing plus error serialisation. The README has no thread/queue example.
- 'No transport can make cancellation finer-grained.' Hedged: cooperative cancel is per-step. A process kill stops mid-step but skips the except handlers and leaves runs.status='running'. Patterns differ in whether they offer a hard kill and what it does to DB state.
- 'Only a ~40k-point viewport ever crosses; bulk data never loads.' Corrected: execute_recipe copies the whole requested span into RAM (execution.py:98 np.asarray(x_full[start:end])). Only the display path can be limited to a decimated viewport. For the destination, the channel is 2,595,600 samples, about 21 MB float64, not 183 MB.
- 'runs row written before and after each step is a reload-proof progress channel.' Corrected: current_step is written before each step, and status only at the end or on failure. There is no stale-run detection for hard kills.
- 'Pyodide native FS needs permission each session.' Hedged: MEMFS, Chromium-only mountNativeFS and manual syncfs are confirmed from 2022-dated docs. 'Each session' is not stated. Worker.terminate is not checked against the PyScript docs.
- 'Tauri kill() provably does not stop a PyInstaller sidecar (tauri#11686, open).' Corrected: the issue is closed (2024-11-14). It was reported for --onefile builds, and the fix (process-group spawn) is tracked in plugins-workspace#1332, still open. taskkill workarounds exist. It only matters if cancel is done by kill rather than a cooperative flag. 'UI thinks cancelled while the run writes' is inferred.
- 'pywebview has an open rough edge (#906).' Corrected: #906 closed 2022-07-04. pywebview threading and evaluate_js are confirmed. The WebView2 details and the whole PySide6 QWebChannel/QThread story are unverified.
- 'NiceGUI and Flet hide a WebSocket split.' Hedged: plausible for NiceGUI (reconnect_timeout, FastAPI + Vue/Quasar, protocol not named). Flet is unverified. The same classification applies to Panel.
- 'gRPC needs a .proto per interchange type plus gRPC-Web, not justified.' Not checked (judgement). The premise that browsers need gRPC-Web or Connect is standard.
- 'Panel 2.0/3.0 roadmap implies API churn / improved error messages will land on a 2027 timeline.' Unverified. The doc gave Panel 2.0 as ~Q2 2026 and never checked whether it shipped. The installed Panel is 1.9.3.

## 4. Candidate families — state of the evidence (neutral)

### Python-native web (server-rendered Python UI talking to a JS client over WS/HTTP)

**Still viable:** Panel (rebuilt architecture, HoloViews/Bokeh; optionally Panel Plotly pane for viewport); Dash (Plotly); NiceGUI; Solara; Streamlit; Reflex (Node toolchain required)

**Eliminated:**
- Datashader-in-HoloViews as the signal renderer — removed after the blank-pane incident and made moot by the decimator — UI/plots.py:43-63; plotting-libraries (confirmed)
- Matplotlib/ipympl or Altair JupyterChart as the interactive viewport host outside Jupyter — conditional elimination, host not confirmed — plotting-libraries (not verified)

**Best case.** In-process with Working/: direct callbacks, a shared cancel flag, and core exceptions in the same Python process (core-transport, partially confirmed). No new transport. The existing decimator, hv.streams.RangeX viewport and render_value's HoloViews dispatch port directly on the HoloViews route. Per-call hv.save(backend='matplotlib') gives vector export without touching interactive render. Panel's Plotly pane exposes a first-party `viewport` param (confirmed). Kaleido gives Plotly a same-Figure SVG/PDF export. A Playwright console gate already exists in the repo. spikeinterface-gui is a maintained Panel+Bokeh scientific multi-view reference (confirmed).

**Worst case.** Rendering still crosses a Python-to-JS channel, and the documented failure class (a callback exception caught and logged server-side, with the pane left blank) is not shown to be escapable on Panel. HoloViews also maps some exceptions to empty frames. No doc shows Dash, NiceGUI or Solara surfacing a server-side callback exception loudly in the browser. Export is two renderers (Bokeh plus Matplotlib) or needs a Chrome/Selenium dependency (Bokeh export, Kaleido). Non-plot interchange types need custom components outside HoloViews. Streamlit's rerun model and Reflex's Node toolchain add friction, though the Reflex ESM breakage evidence is now stale. Nothing is measured at #9's atlas density.

### JS/TS frontend + Python backend (FastAPI SSE/WebSocket)

**Still viable:** React + FastAPI; Vue + FastAPI; Svelte/SvelteKit + FastAPI; SolidJS + FastAPI; Chart layer options: uPlot, ECharts, Plotly.js, D3/d3-zoom, Lightweight Charts; React Flow available for a chain surface

**Eliminated:**
- PyScript/Pyodide as the primary transport — MEMFS/no shared filesystem by default, hard-kill-only cancel, reload destroys heap — core-transport (partially confirmed)
- Observable Plot as the interactive signal view — pan/zoom unshipped (#1590) — plotting-libraries (confirmed); still a candidate for static/report facets
- VisPy — no documented viewport event, raster-only export — plotting-libraries (API pages only)
- gRPC and ZeroMQ as the transport — judged over-ceremonial or protocol-less at this scale — core-transport (judgement, not checked)

**Best case.** The largest documentation and training corpus (React), with an explicit modern testing idiom (Testing Library). Loud, structured 422 validation at the API boundary. Viewport APIs are purpose-built: d3-zoom, uPlot setScale, Lightweight Charts ranges, ECharts dataZoom. D3 or ECharts SVG mode can make the live render the export. File-path handoff means only decimated viewports cross the wire. The UI is fully decoupled from the frozen core, which fits 'nothing below the boundary knows a browser exists'.

**Worst case.** High core distance. A new transport has to be designed, covering thread-to-loop handoff, disconnect-to-cancel wiring, reload reconciliation against a runs row that does not record step completion, and serialisation of all seven interchange types (unanalysed by any doc). The decimator and render_value must be re-exposed over HTTP or reimplemented. Seven-type dispatch is built from scratch. The best viewport libraries (uPlot, Lightweight Charts) have no vector export, so a second export tool is needed. There is idiom churn: Svelte 5 runes, React 19 test-utils removal. There is a second toolchain (Node), and its sign-off is required. The throughput advantage is asserted from corpus size, not demonstrated.

### Desktop-native Qt/PySide6 (no browser)

**Still viable:** PySide6 + PyQtGraph (optionally Matplotlib FigureCanvasQTAgg for figures)

**Best case.** No browser anywhere. In-process with Working/, with a clean cooperative cancel over QThread signals. PyQtGraph sigRangeChanged and SVGExporter ('preferred method for publication graphics') are confirmed. phy and MNE-QT-Browser (BSD-3, maintained) show pyqtgraph handling multi-hour multichannel traces. spikeinterface-gui ships both a Qt and a Panel backend over one view model, a precedent for keeping the view contract stack-portable. pytest-qt is a first-party-adjacent test harness with no shadow DOM.

**Worst case.** Every one of the seven type renderers is a hand-built native widget. There is no web output at all, which conflicts with the 'website' and report goal and needs a separate HTML/report path (unassessed). PyQtGraph's cited 60 Hz ceiling (~30k) is below the 40k cap. Its loud-failure behaviour is unverified. Signal-based tests do not prove paint. PySide6 as a pip wheel in the shared conda env is untried, and licensing is unchecked. The documentation and agent-training corpus for Qt widget code, compared with web frameworks, is unassessed.

### Desktop-wrapped webview (pywebview, Qt WebEngine+QWebChannel, Tauri, Electron)

**Still viable:** pywebview + JS frontend (in-process Python); Qt/PySide6 WebEngine + QWebChannel (in-process Python); Tauri + Python sidecar (or inner localhost server); Electron + Python child (or inner localhost server)

**Best case.** pywebview and QWebChannel keep the core in-process with a plain cancel flag while using a web UI and web chart libraries. Tauri and Electron can embed an inner localhost FastAPI server, which reduces them to the JS+FastAPI family and gives a process that survives a renderer reload. The web frontend keeps an HTML path for reports.

**Worst case.** These wrappers answer none of the render, export, dispatch or throughput questions themselves. They inherit every JS-family cost and add a shell. Tauri needs Rust plus PyInstaller freezing of numpy, scipy and aeon, and a kill of a --onefile sidecar is reported not to terminate it on Windows (fix still open upstream). Electron adds Node and electron-builder, and a frozen Python child brings back the double-process kill risk. pywebview and QWebChannel are single-process (losing the process loses the run), and their bridge failure modes are weakly sourced (the doc itself says pilot it). The packaging problem these tools solve does not exist on a single localhost machine.

## 5. Decision forks for the human (no recommendation)

### F1. Browser-rendered UI vs desktop-native (Qt/PySide6, no browser)

*Bears on ticket #9's outcome:* yes

**Options:**
- Browser-rendered (Python-native web, or JS/TS + Python backend, optionally webview-wrapped)
- Desktop-native Qt/PySide6 + PyQtGraph, with a separate path for HTML/report output

**Why it is a fork.** Both are admissible under the map. Each wins a different binding criterion: silent-failure surface and core distance on one side, report/'website' output and web ecosystem on the other. No doc resolves the trade, because none evaluates HTML/report output for any candidate. #9 bears on it because it sets a web-shaped layout target and names Pipelines/ figures as the export target.

**Evidence.** Browser: the downstream goal is plots and reports the user calls 'the website'. Ticket #9 fixes the interface target as .pen pages, a 1440 px web-style shell with a 64 px nav rail and 12-column card grid. Web stacks keep an HTML output path for free. Desktop: no browser boundary to fail silently. PyQtGraph range signal and SVG export are confirmed. The core stays in-process with clean cancel. Domain precedent exists (phy, MNE-QT-Browser). Map #4 does not bind a browser target; UI_CONTEXT marks the whole stack open. Against desktop: every seven-type renderer is a native widget, the 60 Hz ceiling is below the 40k cap, loud failure is unverified, and there is no web output.

### F2. Python-authored UI (in-process core) vs JS/TS frontend over a new transport

*Bears on ticket #9's outcome:* no

**Options:**
- Python-native web (Panel rebuilt, Dash, NiceGUI, Solara, Streamlit, Reflex)
- JS/TS framework (React/Vue/Svelte/Solid) + FastAPI SSE/WebSocket

**Why it is a fork.** It is the heaviest-weighted criterion (agentic throughput and loud failure), and the evidence on both sides is partial. The decisive loud-failure claims were partially confirmed or refuted, and nothing was built or run. Ticket #12 also excludes transport from scope, but this fork effectively decides the transport family.

**Evidence.** Python-native: callbacks, cancel flag and core exceptions are in-process. The decimator and HoloViews render_value port directly. No transport to design. JS/TS: the largest docs corpus and a modern single testing idiom (React). Purpose-built viewport libraries. Loud API-boundary validation. ### core-transport

**Summary.** The doc surveys how a non-Python frontend could reach the synchronous, blocking `execute_recipe` core. It covers HTTP+SSE, WebSockets, Tauri, Electron, pywebview, Qt/PySide QWebChannel, Pyodide/PyScript, Python-native in-process frontends, gRPC, ZeroMQ, and handing over file paths instead of bytes. Its repo grounding checks out: the signature at Working/execution.py:180, cancel checked between steps at :328, runs.current_step written at :335 before on_progress at :337, on_step_result at :438, the except handlers at :453-459, the mmap load at :94, CLUSTER_ROUTING_CEILING_S=900, and the private _recipe_prefix_hash import at UI/analyse/chain_state.py:43. Two findings hold across every pattern. First, cancellation granularity belongs to the core, so no transport can change it. Second, on a shared filesystem only a path and a decimated viewport need to cross, so the bulk-data question stops separating most patterns. Among transports for a browser frontend, FastAPI with SSE or WebSockets and a thread+queue bridge is shown as the cheapest wiring. Pyodide is judged not viable because of the browser sandbox filesystem and Worker.terminate(). Tauri gets one cited silent failure: kill() does not stop a PyInstaller exe on Windows. The weakest and most decision-relevant section is D2. It presents Panel/Streamlit/Dash as truly in-process with visible failures and 'no transport layer to fail silently'. That clashes with the repo's blank-pane record and is inconsistent with the doc's own treatment of NiceGUI/Flet. The doc barely touches the criteria that weigh most in the stack decision: agentic throughput, headless render proof, static export, and how the six non-Signal interchange types reach a renderer.

#### Load-bearing claims and verdicts

**`python-native-no-transport`** — *judgement* — verdict: **judgement_not_checked**

- Claim: A truly in-process Python frontend (classic Panel/Streamlit/Dash, this app's current architecture) collapses all six transport concerns to zero: progress is a direct callback, cancellation a shared flag, failures are ordinary Python exceptions 'visible by default', and 'there is no transport layer here to fail silently'. It is 'the ceiling every transport above is trying to approximate, not exceed'.
- Cited: CLAUDE.md, Panel surfaces section (no external source for Panel/Streamlit/Dash architecture)
- Moves: Panel (rebuilt architecture), Streamlit, Dash, NiceGUI/Flet, all non-Python frontends, silent-failure criterion
- Why load-bearing: If Panel actually renders through a Python-to-BokehJS WebSocket and fails silently at the browser boundary (which is what the three blank-pane incidents were), the incumbent gets no structural transport advantage and scores badly on the loud-vs-silent-failure part of the heaviest criterion. The doc's framing gives it exactly that advantage.
- Verifier evidence: Judgement, but its factual premise is false for Panel. Bokeh server docs (docs.bokeh.org server_introduction) say the server's purpose is 'to synchronize data between the underlying Python environment and the BokehJS library running in the browser', converting Python models to JSON. So Panel has a Python-to-BokehJS channel with a browser-side renderer. The repo's own CLAUDE.md (Panel surfaces section) says a construction test 'cannot catch a present pane that throws in the browser - which is what actually happened both times', and that a broken dynamic map renders as 'a silently blank pane, not an error'. The doc's own table (line 50) calls Panel 'truly in-process', which contradicts that. Callbacks and cancel flags are in-process on the Python side. Rendering failures are not.
- **Correction:** Panel is in-process for the core (callbacks, cancel flag, and Python exceptions on the server side) but renders over a Bokeh server WebSocket into BokehJS. Browser-side failures there are silent by default, as this repo has seen twice. It should not be scored as having no transport and no silent failures; it belongs with the WebSocket pattern for rendering failures, like NiceGUI/Flet.

**`sse-thread-queue-bridge`** — *external_fact* — verdict: **partially_confirmed**

- Claim: FastAPI plus sse-starlette's EventSourceResponse, with execute_recipe on a worker thread pushing on_progress/on_step_result into an asyncio.Queue, is 'a direct, mechanical mapping' onto the existing callback signature with no protocol design, needs only pip (no new toolchain), and is the cheapest pattern surveyed.
- Cited: FastAPI GitHub Discussion #9398; sysid/sse-starlette README/DeepWiki; FastAPI Background Tasks docs
- Moves: any non-Python web frontend (JS framework + FastAPI), WebSockets pattern, Tauri/Electron with inner localhost server
- Why load-bearing: This is the bridge every browser-based non-Python stack would sit on. If it needs real protocol work or core changes, those stacks lose development throughput against in-process options.
- Verifier evidence: The sse-starlette README (github.com/sysid/sse-starlette) documents EventSourceResponse over async generators, `await request.is_disconnected()`, and CancelledError on disconnect. It has 'No direct queue or thread-based sending examples'. The doc itself (lines 75-76) admits a disconnect 'cancels the generator, not the thread' and needs a manually wired threading.Event. asyncio.Queue is not thread-safe: a worker thread has to use loop.call_soon_threadsafe (or a thread-safe queue), which the claim does not mention. Pip-only is plausible. I did not open FastAPI Discussion #9398.
- **Correction:** Pip-only and structurally workable, but not zero design. You need call_soon_threadsafe (or equivalent) to hand off from thread to loop, disconnect-to-cancel wiring written by hand, and event framing and error serialization for SSE. The README has no thread/queue example for this.

**`cancel-is-core-property`** — *repo_fact* — verdict: **partially_confirmed**

- Claim: Cancellation is cooperative and checked once per step before it starts; no transport can make it finer-grained, so patterns differ only in how reliably the cancel signal arrives and what happens to DB state if it doesn't.
- Cited: Working/execution.py:328 (verified)
- Moves: all candidates
- Why load-bearing: This takes cancellation off the list of things that separate stacks. If a transport could interrupt in-flight work, patterns with native cancel (gRPC, subprocess kill) would gain ground.
- Verifier evidence: Working/execution.py:328-329 (origin/research/core-transport): `if should_cancel is not None and should_cancel(): raise RecipeCancelled(f"Cancelled before step {i} ...")`. That is the only check, so the cooperative, per-step part is confirmed. But a transport or host that kills the process (subprocess kill, Worker.terminate) does stop work mid-step, which the doc itself describes for Pyodide at lines 293-297.
- **Correction:** Cooperative cancellation is per-step and no transport refines it. A process kill can interrupt mid-step, but it is not cooperative: it skips the except handlers at :453-458 and leaves the run row at status 'running'. Patterns differ in whether they offer that hard kill and what it does to DB state, not only in how reliably the signal arrives.

**`file-path-handoff`** — *judgement* — verdict: **judgement_not_checked**

- Claim: Because frontend and core always share a filesystem, the bulk channel array never needs to cross any transport except Pyodide's. Python mmaps the file (execute_recipe already uses np.load mmap_mode='r') and only a ~40,000-point decimated viewport is shipped.
- Cited: Working/execution.py:94 (verified); ticket #8 fixed context
- Moves: all browser-rendered stacks, Pyodide/PyScript, peak-preserving zoom requirement
- Why load-bearing: If true, bulk data does not separate the non-sandboxed stacks and decimation belongs on the Python side. If a frontend had to hold the full channel, JS-side and WASM-side options would be weighed very differently.
- Verifier evidence: Premise checked: Working/execution.py:94 has `np.load(recording["npy_path"], mmap_mode="r")`. But :98 then does `x = np.asarray(x_full[start:end])`, which copies the whole requested span into memory for execution. So the mmap limits paging to the span, not to a viewport. The 40,000-point figure comes from 'ticket #8', which I did not check. The shared-filesystem premise holds for local stacks only.
- **Correction:** Execution loads the full requested span into RAM (execution.py:98). Only the display path could be limited to a decimated viewport, and that decimation code is not cited or shown to exist.

**`db-row-reload-channel`** — *repo_fact* — verdict: **partially_confirmed**

- Claim: The runs row's current_step/status, written before and after each step, is a transport-independent, reload-proof progress channel every pattern can fall back on after a reload or reconnect.
- Cited: Working/execution.py:335, :442 (verified); schema.py current_step column (verified)
- Moves: HTTP+SSE, WebSockets, Tauri, Electron, pywebview, Qt/PySide
- Why load-bearing: This is what makes surviving a frontend reload cheap for every transport. Without it, WebSocket and in-process-desktop options would need much more state machinery.
- Verifier evidence: execution.py:335 `update_run(conn, run_id, current_step=i)` runs before each step, after the cancel check. :442 writes status='completed' only once, after the loop. :454 and :458 write status='failed' on cancel or exception. No update_run call runs after each individual step. schema.py:337 has ('current_step','INTEGER').
- **Correction:** current_step is written before each step, and status only at the end (completed/failed). There is no per-step 'after' write, so the row says which step started, not which finished. A hard-killed process leaves status='running' permanently, so a reload fallback needs stale-run detection.

**`pyodide-not-viable`** — *external_fact* — verdict: **partially_confirmed**

- Claim: Pyodide/PyScript cannot use the shared filesystem: its FS is a virtual in-memory Emscripten FS, and native access is Chromium-only, needs permission each session, and is not synced by default. Worker.terminate() is the only cancel and it bypasses execute_recipe's crash-safety. A reload destroys the WASM heap.
- Cited: Pyodide 'Dealing with the file system' (retrieved via cached/search access after 403); PyScript Web Workers guide (docs.pyscript.net/2026.3.1); uncited 'community guidance' for worker usage
- Moves: PyScript/Pyodide stacks
- Why load-bearing: This is the only pattern the doc rules out outright. It removes any in-browser Python option from the stack shortlist.
- Verifier evidence: Pyodide docs (raw github docs/usage/file-system.md; pyodide.org returned 403) say: 'The default file system used in Pyodide is MEMFS... data stored in MEMFS will be lost when the page is reloaded'; 'The File System Access API is only supported in Chromium based browsers: Chrome and Edge (as of 2022/08/18)'; 'the changes in the mounted file system is not synchronized by default' (syncfs required). A permission check (`permissionStatus !== 'granted'`) is shown, but nothing says permission is needed 'each session'. I did not check the Worker.terminate claim against PyScript docs.
- **Correction:** MEMFS, Chromium-only mountNativeFS, and manual syncfs are confirmed. 'Permission each session' is not stated in the Pyodide docs (it is browser File System Access behaviour). Note too that the source date is 2022, so current browser support may be wider.

**`tauri-pyinstaller-kill`** — *external_fact* — verdict: **partially_confirmed**

- Verifier evidence: tauri-apps/tauri#11686 (state closed, created and closed 2024-11-14): 'child.kill() does not successfully terminate the process opened by the sidecar... #### Overreach or errors found by the reader

- Section D2 misreads a repo fact and the incumbent's architecture. It calls Panel 'truly in-process' with failures that are 'ordinary Python exceptions — visible by default' and says 'there is no transport layer here to fail silently in the first place'. CLAUDE.md says the blank-pane failure was 'a present pane that throws in the browser', and the binding record is a DynamicMap that throws and renders empty with only a log warning. That is a silent failure at exactly the Python-to-browser boundary the doc claims does not exist. Panel is served by a Bokeh server talking over a WebSocket to BokehJS; Dash callbacks are HTTP requests from a React client; Streamlit uses a WebSocket. These are general knowledge, not verified in this stage. The doc reclassifies NiceGUI/Flet as 'Pattern B with the boilerplate hidden' but does not apply the same test to Panel, which is inconsistent.
- Calling the in-process Python frontend 'the ceiling every transport above is trying to approximate, not exceed' gives Panel incumbency credit. The binding constraints give no incumbency credit or penalty. It also inflates the silent-failure criterion in Panel's favour against the repo's own history.
- Internal contradiction in pattern A. A2 wires client disconnect to flip the should_cancel flag. A4 and the table say the run 'survives' a reload because the client re-polls the runs row. With the wiring A2 describes, a page reload drops the SSE connection and so cancels the run.
- The claim that Pyodide's Worker.terminate() is 'uniquely bad' and 'the only pattern surveyed that can bypass execute_recipe's own crash-safety' contradicts the doc's own C2 text. There, kill() on Windows maps every signal to 'forceful termination'. A hard-killed sidecar or child process also runs no except/finally and leaves the runs row status='running', and so does a Tauri kill that succeeds. The distinction as stated is wrong.
