## In plain words

A recording is a long list of voltages taken at regular ticks. To use one we must know how often the
ticks came (the sampling rate) and what the numbers are measured in (volts or millivolts). These files
store their clock as a MATLAB object Python cannot open, so the rate is either read from that clock
(after `scripts/export_mat_time.m` turns it into plain seconds in MATLAB) or, failing that, worked out
from the length: a file holding exactly 20 days of samples at 10 per second, plus the closing sample,
is taken to be 10 Hz and labelled *inferred, not read*. The unit comes from the size of the numbers:
values around ±1 are volts, values in the hundreds are millivolts.

## How to reproduce

From the main checkout, in order (each `--dry-run` writes nothing):

    python scripts/derive_mju26a_fs10.py --dry-run
    python scripts/derive_mju26a_fs10.py
    python scripts/derive_raw_mat.py CO LM SH SO F2B L_R_Aug_26_PD_raw --dry-run
    # optional, to READ the rates instead of inferring them (MATLAB R2025b):
    #   matlab -batch "addpath scripts; export_mat_time()"     -> DATA/derived/time_axes/<stem>_time.mat
    python scripts/derive_raw_mat.py CO LM SH SO F2B
    python scripts/derive_raw_mat.py L_R_Aug_26_PD_raw         # only once its rate is read or stated

Each derived directory's `manifest.json` carries the full reasoning (`fs_note`, `units`, `resampling`),
and each registration is in the audit log (Settings › Audit).
